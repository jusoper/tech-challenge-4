Do DevOps ao MLOp s: A Evolução das Práticas de Engenharia
O movimento DevOps emergiu na segunda metade dos anos 2000 como resposta ao abismo entre desenvolvimento de software e operações de infraestrutura:
ao unir cultura, automação, medição e compartilhamento, reduziu drasticamente o tempo entre escrever código e entregar valor, e práticas como integração contínua
(CI), entrega contínua (CD) e infraestrutura como código (IaC) viraram pilares da engenharia moderna. Ao aplicá -los ao machine learn ing, surge um problema fundamental: modelos de ML não são apenas código — são a interseção de três artefatos que evoluem de forma independente (código, dados e hiperparâmetros), e uma mudança em qualquer um deles pode alterar o comportamento do sistema em produção mesmo com os testes de software passando. Esse insight, formalizado por
Sculley et al. (2015) em "Hidden Technical Debt in Machine Learning Systems",
explica por que o ML exige uma extensão especializada do DevOps: o MLOps.
O MLOps (Machine Learni ng Operations) é o conjunto de práticas, ferramentas e princípios culturais que automatizam e monitoram todas as etapas de sistemas de
ML, da preparação dos dados ao monitoramento em produção. Segundo Kreuzberger et al. (2022), há três níveis de maturidade : o nível 0, com processos manuais e modelos estáticos; o nível 1, com pipelines de treinamento automatizados e retreinamento contínuo; e o nível 2, com CI/CD totalmente automatizado para ML —
e é na transição do nível 1 para o 2 que a validação contínua s e torna essencial. Uma analogia útil é a manufatura: o código é a máquina, os dados a matéria -prima e o modelo o produto — e uma fábrica moderna não testa só o produto: monitora a matéria -prima e a máquina em cada etapa.
CI/CD para Dados: Fundamentos e Pri ncípios
A Integração Contínua (CI) para dados vai além de rodar testes de unidade a cada commit: envolve validar automaticamente, a cada chegada de novos dados
(batch ou streaming), a integridade do schema, as distribuições estatísticas (os dados de hoje s ão semelhantes aos de ontem?), a completude e a consistência das

(estratégia champion -challenger) e deploy automático — ou com aprovação humana
— do vencedor.
Um conceito exclusivo do ML que emerge daí é o Treinamento Contínuo (CT
— Continuous Training): quando as distribuições de produção se desviam significativamente das de treinamento — o data drift visto em aulas anteriores —, o pipeline deve disparar automaticamente um novo ciclo de treinamento com dados recentes. Segundo Chen et al. (2021), a falta de CT é uma das principa is causas de degradação silenciosa de modelos em produção — o modelo continua funcionando tecnicamente, mas suas previsões ficam progressivamente menos precisas à medida que o mundo evolui e os dados de treino envelhecem.

MLflow: A Plataforma de Rastreamento e Ciclo de Vida de Modelos
O MLflow é uma plataforma open -source criada pela Databricks em 2018 para o gerenciamento do ciclo de vida de experimentos e modelos, organizada em quatro componentes: MLflow Trac king (registro de experimentos), MLflow Projects
(empacotamento de código reproduzível), MLflow Models (formato de modelo agnóstico a frameworks) e MLflow Model Registry (governança do ciclo de vida). Para a validação contínua, os pilares são o Tracking e o Registry.
MLflow Tracking: Data Logging e Experiment Management
O MLflow Tracking é um sistema de logging distribuído para registrar, consultar e comparar execuções (runs): cada run registra parâmetros, métricas, tags, artefatos
(modelos, gráficos, datas ets) e dados de entrada — na hierarquia Tracking Server →

Experiments → Runs → (Params, Metrics, Artifacts) . Um aspecto subestimado é o data logging: a partir do MLflow 2.4, mlflow.log_input() associa um dataset a uma run,
registrando nome, hash SHA256 (para verificar se o mesmo dataset é usado em diferentes runs), fonte e contexto de uso — o primeiro passo para um pipeline de validação contínua rastreável. O autolog (mlflow.autolog()) captura automaticamente parâmetros, métricas e artefatos de ma is de 15 frameworks (scikit -learn, XGBoost,
LightGBM, TensorFlow, PyTorch) e pode ser combinado com logging manual de métricas de validação de dados do domínio.
MLflow Artifact Tracking e Model Registry
O sistema de artefatos transforma runs isoladas em experimentos rastreáveis:
qualquer arquivo — modelos serializados, gráficos, relatórios de validação, datasets,
checkpoints — pode ser registrado como artefato de uma run, em um backend configurável (local, S3, GCS, Azure Blob ou o storage do D atabricks), associado permanentemente a ela. Um padrão importante para validação contínua é usar artefatos como "contrato de qualidade" entre etapas: a ingestão registra o relatório de validação do Great Expectations e a etapa seguinte só prossegue se o ar tefato existir e "validation_passed" for True — os artifact -driven pipeline gates, que impedem que dados inválidos avancem e criam uma cadeia auditável. Já o Model Registry cuida da governança dos modelos promovidos à produção (o Tracking cuida da descober ta): a versão clássica define os estágios Staging, Production e Archived, e a partir do MLflow
2.9 aliases customizáveis — "champion", "challenger", "baseline" — substituem os estágios fixos, permitindo fluxos de promoção mais flexíveis.
Databricks e Unity Catalog: Governança Unificada de Dados e Modelos
O Databricks é uma plataforma de dados e IA construída sobre o Apache Spark,
fundada em 2013 pelos criadores do Spark, com ambiente unificado para engenharia de dados, ciência de dados e MLOps em escala — e o MLflow gerenciado como componente nativo. O Unity Catalog, lançado em 2022, é seu sistema de governança:
um metastore centralizado para tabelas e views SQL, volumes (dados não estruturados), modelos do MLflow, features do Feature Store e arquivos em sto rage cloud, com controle de acesso granular (RBAC), auditoria completa e lineage

Data Observability e Lineage Tracking
Data observability adapta os princípios de observabilidade de sistemas — logs,
métricas e traces — aos dados. Segundo Barr Moses, co -fundadora da Monte Carlo
Data, seus cinco pilares são freshness (os dados estão atualizados?), distribution (as distribuições estão dentro do esperado?), volume, s chema (a estrutura não mudou inesperadamente?) e lineage (conseguimos rastrear origem e caminho?), cada um ligado a um tipo de falha e a uma estratégia de monitoramento. O Databricks a implementa combinando o Delta Lake — formato com transações ACID cujo transaction log detalhado permite auditoria e rollback para qualquer versão anterior
(time travel) —, o Lakeflow (orquestrador nativo) e integrações como o Great
Expectations.
O lineage tracking documenta automaticamente a origem de um dado e seu caminho co mpleto da fonte ao destino, respondendo perguntas críticas para auditoria e debugging: "qual modelo foi treinado com esse dataset?", "se este dado estiver errado, quais modelos em produção foram impactados?". O Unity Catalog o captura em três níveis — column-level, table -level (grafo de dependências entre tabelas, views e modelos) e model lineage (modelos conectados aos dados de treinamento) — a partir das queries executadas, sem anotações manuais no código.

e acionável (direcionar a pessoa certa à ação certa) — um alerta que apenas diz "algo deu errado" é quase tão inútil quanto nenhum. O Databricks oferece alertas nativos

HTTP. O padrão recomendado é logar as métricas de qualidade no MLflow e acionar as notificações pelo Lakeflow.
Databricks Asset Bundles: Inf raestrutura como Código para MLOps
O Declarative Automation Bundles (DABs) — também conhecido como
Databricks Asset Bundles — é a solução nativa para definir, versionar e implantar recursos do workspace como código declarativo: em vez de criar jobs, pipeli nes e configurações pela interface gráfica, descreve -se toda a infraestrutura em YAML versionado no Git, no princípio de Infrastructure as Code popularizado por Terraform e Ansible — um único repositório contém o código dos modelos e a definição de jobs,
schedules, permissões e artefatos MLflow, reproduzindo todo o ambiente em qualquer workspace com um comando. O coração do bundle é o databricks.yml , que define nome, variáveis, arquivos de recursos e targets (ambientes de deploy): cada target corresponde a um workspace e pode sobrescrever variáveis, permitindo o mesmo código em dev, staging e prod sem duplicação. Os recursos ficam em YAML na pasta resources/ — jobs multi -task, pipelines, modelos, experimentos e monitores do
Lakehouse Monitoring —, e a interp olação de variáveis (${var.catalog_name},
${bundle.target}) garante consistência entre ambientes.
O ciclo de vida é operado pela Databricks CLI — validate verifica sintaxe e referências sem deploy (útil em CI), deploy cria ou atualiza os recursos, run disp ara
um job e destroy remove tudo o que o bundle criou; no modo development, os jobs recebem o prefixo do usuário e os schedules ficam pausados:
databricks bundle validate databricks bundle deploy --target dev databricks bundle run model_training_job --target dev databricks bundle destroy --target dev

Compl iance e Governance em Pipelines de ML
A conformidade regulatória é frequentemente subestimada no desenvolvimento, mas torna -se crítica em saúde, finanças, seguros e crédito: GDPR,
LGPD e o EU AI Act (em vigor desde 2024) impõem obrigações sobre como sistemas automatizados de decisão devem ser documentados, auditados e explicados aos afetados. O MLflow e o Databricks facilitam essa conformidade: o Unity Catalog mantém um audit log detalhado de acessos e transformações, o Model Registry registra quem pr omoveu cada versão, quando e com qual justificativa — um trail de aprovações essencial em ambientes regulados — e, conforme anunciado em junho de 2025, o MLflow no Databricks passou a suportar todos os compliance profiles da plataforma, incluindo HIPAA, PC I-DSS e FedRAMP Moderate (Databricks, 2025).
Um conceito prático nesse contexto é o Model Card — documento estruturado que descreve um modelo de forma padronizada (dados de treinamento, métricas por subgrupo, limitações, considerações éticas), no formato e stabelecido pelo Google AI
(Mitchell et al., 2019) e registrável no Model Registry; integrá -lo ao CI/CD garante que cada versão em produção tenha sua documentação de compliance atualizada automaticamente.
Integrando GitHub, MLflow e Databricks: Um Pipeline CI/CD Completo
Chegamos à síntese: um único pipeline de CI/CD para dados e modelos, com o GitHub como repositório e gatilho, o GitHub Actions como orquestrador de CI, o
MLflow como rastreamento central e o Databricks como plataforma de processamento e dep loyment — padrão de equipes de alta maturidade, alinhado às práticas
Validação Contínua com MLOps, MLflow, AWS e Azure recomendadas por Kreuzberger et al. (2022). O fluxo: ao abrir um pull request com mudanças no código do pipeline de dados ou de treinamento, o GitHub Actions dispara testes unitários e um treino em ambiente de testes; aprovado e mergeado na branch main, um segundo workflow dispara o pipeline completo no Databricks — treinamento,
registro no MLflow e promoção automática ao alias "challenger" no Model Registry.
É a implementação prática do " pipeline as code": o pipeline de CI/CD é código de primeira classe, versionado junto com o modelo e os testes — qualquer mudança é revisada em pull request, testada e documentada no histórico do Git. Na videoaula,
você verá como configurar os secrets do Gi tHub e as permissões do Databricks para que ele funcione de ponta a ponta.

### Mercado, Cases E Tendências
A adoção de MLOps atingiu maturidade acelerada nos últimos anos. De acordo com a Fortune Business Insights, o mercado global de MLOps foi avaliado em USD
2.98 bilhões em 2025 e deve crescer para USD 89.91 bilhões até 2034. Esta expansão é impulsionada pela crescente regulamentação de sistemas de IA, pelo aumento da complexidade dos pipelines de ML em produção e pela maturidade das ferramentas disponíveis. O Nubank, fintech brasileira referência global em uso de ML para crédito e personalização financeira para mais de 100 milhões de clientes em três países,
opera um ambiente Databricks com uma ampla base de usuários e grande volume de notebooks e jobs em pro dução (Databricks, 2024). A capacidade de rastrear o lineage de dados — saber exatamente com quais dados cada modelo foi treinado — é fundamental para atender às exigências do Banco Central do Brasil relacionadas à explicabilidade de decisões de crédito au tomatizadas.
O Airbnb, por sua vez, desenvolveu internamente o Zipline — uma plataforma declarativa de engenharia e gerenciamento de features para ML que serve como fonte única de verdade para todas as features utilizadas pelos modelos em produção da empresa. O Zipline garante consistência entre treino e inferência por meio de computações point -in-time corretas, evitando data leakage e assegurando que os modelos utilizem exatamente os mesmos dados tanto no treinamento offline quanto no serving online em tempo real. Com essa abordagem, o Airbnb reduziu de meses para dias o tempo necessário para criar novas features de ML, além de incorporar monitoramento automático de qualidade de dados às próprias definições de features
(Zanoyan; Shapiro, 2019).
Conforme já vimos em out ras aulas, uma tendência crescente e complementar ao MLOps é a adoção de Data Contracts — acordos formais que definem o esquema,
a semântica e as garantias de qualidade dos dados trocados entre produtores e consumidores. Segundo levantamento da Monte Carlo Data, a combinação de arquitetura data mesh com data contracts e plataformas modernas de observabilidade reduz drasticamente os gargalos dos times centrais de dados, melhorando simultaneamente qualidade, freshness e descoberta de dados entre domínios ao eliminar silos (Monte Carlo Data, 2026). O MLflow 3.0, lançado em 2025, trouxe capacidades de observabilidade nativas para aplicações de IA generativa —
