O Problema da Reprodutibilidade
Zaharia et al. (2018) identificaram que o ciclo de vida de ML envolve desafios únicos que ferramentas de software tradicionais não resolvem , como e xperimentação massiva (cientistas de dados testam centenas de combinações de hip erparâmetros,
features e algoritmos ), múltiplos ambientes (código que funciona no notebook pode não funcionar em produção ), dependências complexas (modelos dependem de versões específicas de bibliotecas, dados e código ) e colaboração (múltiplas pessoas trabalhando nos mesmos modelos precisam compartilhar resultados ).
O MLflow foi criado para resolver esses problemas com uma plataforma modular e extensível.
MLflow tracking
O componente de Tracking é o coração do MLflow. Ele permite registrar e consultar expe rimentos de ML.
Conceitos fundamentais:
• Experiment: Agrupamento lógico de runs relacionados ( ex.: "fraud -
detection -model") .
• Run: Uma execução específica de código de ML, com seus parâmetros,
métricas e artefatos .
• Parameters: Inputs do experimento (hiperparâmetros, configurações) .
• Metrics: Outputs numéricos (acurácia, loss, F1) .
• Artifacts: Arquivos produzidos (modelo treinado, gráficos, datasets) .
• Tags: Metadados adicionais (autor, versão do dataset, objetivo) .

MLflow Tracking Server
O Tracking Server pode ser configurado de diferentes formas:
Local: Armazena dados no filesystem l ocal. Bom para desenvolvimento individual.
Remoto: Servidor centralizado acessível por toda a equipe. Componentes:
backend store (banco de dados como PostgreSQL, MySQL para parâmetros e métricas ) e a rtifact store (storage como S3, GCS, Azure Blob para arte fatos e modelos ).

Comparando Runs
A UI do MLflow permite comparar runs visualmente:
• Tabela com parâmetros e métricas lado a lado .
• Gráficos de métricas ao longo de épocas .
• Scatter plots de parâmetros vs métricas .
• Filtros e ordenação por qualquer campo .
Programaticamente, é possível consultar runs v ia API:
from mlflow.tracking import MlflowClient client = MlflowClient()
runs = client.search_runs( experiment_ids=["1"],
 filter_string="metrics.f1_score > 0.9",
 order_by=["metrics.f1_score DESC"],
 max_results=10
)
Model Registry
O Model R egistry é o componente do MLflow para gerenciamento de modelos em produção.
Conceitos incluem Registered Model (um modelo nomeado no registry como
"fraud -detector") , Model Version (uma versão específica do modelo como versão 3) ,

Stages/Aliases (estados do modelo no ciclo de vida ) e Descriptions (documentação do modelo e suas versões ).
Workflow de promoção: Development → Staging → Production → Archived
• Cientista de dados treina modelo e registra no registry .
• Modelo é promovido para Staging para testes de integração .
• Após validação, modelo é promovido para Production .
• Modelo anterior é movido para Archived .
Registrando um modelo:
# Registrar modelo a partir de um run
mlflow.register_model( model_uri="runs:/abc123/model",
 name="fraud -detector"
)
# Promover para produção
client.transition_model_version_stage( name="fraud -detector",
 version=3,
 stage="Production"
)
Model Signatures e Input Examples
Model signatures documentam o contrato de entrada/saída do modelo:

A signature inclui:
• Schema de entrada: nomes, tipos e shapes das features .
• Schema de saída: tipo e sh ape da predição .

Versionamento Completo
Para reprodutibilidade total, precisamos versionar não apena s o modelo, mas todo o contexto:
• Código: Git (commit hash registrado automaticamente pelo MLflow) .
• Dados: DVC (Data Version Control) ou referência ao dataset no artifact store .
• Modelo: MLflow Model Registry .
• Ambiente: Conda environment ou requirements.txt (registrado pelo MLflow) .
• Configuração: Parâmetros logados no MLflow .
Integração com CI/CD
A integração do MLflow com pipelines de CI/CD permite automação completa:
CI para ML: Push de código → trigger de pipeline ; executar testes de dados
(validação de schema, qualidade) ; treinar modelo com MLflow tracking ; executar testes de modelo (performance mínima, fairness) e registrar modelo no registry se testes passam .
CD para ML: modelo promovido para production no registry → trigger de deploy ;
build de container com modelo ; deploy em staging para smoke tests ; deploy em produção (canary ou blue -green) e monitoramento pós -deploy .
O MLflow suporta múltiplos "flavors" para empacotamento de modelos:

• python_function: Formato gené rico que funciona com qualquer modelo
Python .
• sklearn: Modelos scikit -learn .
• pytorch: Modelos PyTorch .
• tensorflow: Modelos TensorFlow/Keras .
• xgboost: Modelos XGBoost .
• transformers: Modelos Hugging Face .
Cada flavor permite serving do modelo de diferentes formas:
• mlflow models serve: Servidor REST local
• Docker container: Para deploy em qualquer infraestrutura
• Cloud endpoints: SageMaker, Azure ML, Databricks
Os autores de "Beginning MLOps with MLflow" destacam que o MLflow não é apen as uma ferramenta de tracking — é uma plataforma que conecta experimentação com produção. A chave é usar o Model Registry como ponto de controle entre desenvolvimento e operação, garantindo que apenas modelos validados cheguem à produção.

### Mercado, Cases E Tendências
O MLflow é mantido pela Databricks e tem uma comunidade open -source ativa com milhões de downloads mensais. Alternativas incluem Weights & Biases (W&B),
Neptune.ai, Comet ML e ClearML, cada uma com foco diferente.
A tendência é a integração cada vez mais profunda entre experiment tracking e model serving, com plataformas oferecendo deploy com um clique a partir do registry. O MLflow 2.x introduziu o MLflow Deployments Server (anteriormente AI
Gateway) para gerenciar endpoints de modelos, incluind o LLMs.
Outra tendência é o uso de feature stores (como Feast e Tecton) integrados com MLflow para garantir que as mesmas features usadas no treino sejam usadas na inferência, eliminando o problema de training -serving skew.
