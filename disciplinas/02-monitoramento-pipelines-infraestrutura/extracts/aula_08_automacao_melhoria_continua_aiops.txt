Continuous Training: O Terceiro Pilar
Em DevOps tradicional, falamos de CI/CD — Continuous Integration e
Continuous Delivery. Em MLOps, adicionamos um terceiro pilar: CT — Continuous
Training.
Kreuzberger et al. (2023) definem CT como o processo de retreinar modelos automaticamente em resposta a triggers específicos, garantindo que modelos em produção permaneçam relevantes à medida que dados e contextos mudam.
Os três pilares de MLOps:
• CI (Continuous Integration): Testar código, dados e modelos automaticamente a cada mudança .
• CD (Continuous Delivery): Deployar modelos validados automaticamente em produção .
• CT (Continuous Training): Retreinar modelos automaticamente quando necessário .
Triggers de retreino
A decisão de quando retreinar um modelo pode ser baseada em difer entes triggers . Schedule -based: retreino em intervalos fixos (diário, semanal, mensal).
Vantagem: simples de implementar, previsível ; desvantagem: pode retreinar desnecessariamente ou não retreinar quando necessário
Performance -based: retreino quando métri cas de performance caem abaixo de um threshold. Vantagem: retreina apenas quando necessário ; desvantagem: requer ground truth para calcular métricas (nem sempre disponível rapidamente) .
Drift-based: retreino quando drift significativo é detectado nos dados de entrada. Vantagem: proativo — detecta problemas antes que afetem performance ;
desvantagem: drift nem sempre implica em degradação de performance .

Event -based: retreino em resposta a eventos específicos : nova fonte de dados disponível , mudança de política de negócio , feedback de usuários indicando problemas e atualização de dependências (nova versão de biblioteca) .
Arquitetura de Pipeline de Retreino Automático
Um pipeline de retreino automático segue o fluxo:
Trigger → Coleta de Dados → Validação de Dados → Feature Engineering
 → Treino → Avaliação → Validação → Registro → Deploy
Guardrails (quality gates): cada etapa tem validações que impedem a propagação de problemas:
• Validação de dados: Schema correto? Volume suficiente? Qualidade aceitável?
• Validação de treino: Modelo convergiu? Métricas dentro do esperado?
• Validação de modelo: Performance superior ao modelo atual? Sem regressões em subgrupos?
• Validação de deploy: Smoke tests passam? Latência aceitável? Sem erros?
Se qualquer guardrail falha, o pipeline para e alerta a equipe — o modelo atual em produção permanece inalterado.
CI para Machine Learning
CI para ML vai além de testes de código — inclui testes de dados e testes de modelo:
Testes de Dados: Schema validation (dados seguem o schema esperado? ),
distribution tests (distribuição dos dados é consistente com o esperado? ),
completeness tests (campos obrigatórios estão preenchidos? ) e f reshness tests
(dados são recentes o suficiente? ).

CD para Machine Learning
Pulicharla (2019) destaca que o deploy de modelos requer estratégias específicas para minimizar risco:
Canary Deployment: Direcionar uma pequena porcentagem do tráfego (ex: 5%)
para o novo modelo, monitorar métricas, e gradu almente aumentar se tudo estiver bem.
Tráfego → Load Balancer → 95% → Modelo v1 (champion) → 5% → Modelo v2 (canary)
Blue-Green Deployment: Manter dois ambientes idênticos. O "blue" serve tráfego atual, o "green" recebe o novo modelo. Após validação, troca r o tráfego de blue para green.
Progressive Rollout: Combinação de canary com automação — o sistema automaticamente aumenta o tráfego para o novo modelo se métricas estão saudáveis,
ou faz rollback se detecta problemas.
Shadow Mode: O novo modelo recebe o mesmo tráfego que o modelo atual,
mas suas predições não são servidas aos usuários. Permite comparar performance sem risco.
Versionamento Completo

• Código: Git (branches, tags, commits) .
• Dados: DVC (Data Version Control) — versiona datasets grandes sem armazená -los no Git .

AIOps: Usando IA para Operar IA
AIOps (Artificial Intelligence for IT Operations) aplica técnicas de ML para automatizar e melhorar operaç ões de TI. Notaro, Cardoso e Gerndt (2021)
categorizam AIOps em três capacidades principais:
Anomaly Detection: Detectar comportamentos anômalos em métricas, logs e traces automaticamente, sem regras manuais.
• Algoritmos: Isolation Forest, Autoencoders, LST M para séries temporais
• Aplicação: Detectar spikes de latência, padrões incomuns de erro, uso anômalo de recursos
Root Cause Analysis (RCA): Identificar automaticamente a causa raiz de um problema a partir de múltiplos sinais.
• Técnicas: Correlação temporal , grafos de causalidade, análise de propagação
• Aplicação: "A latência subiu porque o disco está cheio porque o job de limpeza falhou"
Auto-Remediation: Executar ações corretivas automaticamente quando problemas são detectados.
• Exemplos: Restart de serviços , scale up de recursos, rollback de deploy
• Requer: Playbooks automatizados, guardrails de segurança, limites de ação

LLMs para AIOps
A fronteira mais recente de AIOps é o uso de Large Language Models para análise de logs (LLMs podem interpretar logs em linguagem natural e identificar padrões que regras tradicionais não capturam ), geração de runbooks (dado um a lerta,
gerar automaticamente passos de investigação e mitigação ), c hat-based troubleshooting (engenheiros podem "conversar" com o sistema de observabilidade para investigar problemas ) e s umarização de incidentes (gerar post -mortems automaticamente a partir de dados do incidente ).
Observabilidade Generativa
O conceito de "observabilidade generativa" propõe que sistemas de observabilidade não apenas coletem e exibam dados, mas gerem insights proativamente — identificando tendências, p revendo problemas futuros e sugerindo otimizações antes que humanos percebam a necessidade.

### Mercado, Cases E Tendências
O mercado de AIOps está em rápida expansão, com players como Datadog
(Bits AI), New Relic (AI), Dynatrace (Davis AI) e PagerDuty (AIOps) integrando capacidades de IA em suas plataformas de observabilidade.
A tendência de "closed -loop MLOps" — onde o monitoramento alimenta automaticamente o retreino, que alimenta o deploy, que alimenta o monitoramento —
está se tornando o padrão para organi zações maduras em ML. Isso reduz o tempo entre a detecção de um problema e sua resolução de dias para horas ou minutos.
Regulamentações como a EU AI Act estão impulsionando a necessidade de auditabilidade e rastreabilidade em sistemas de ML automatizados, exigindo que organizações demonstrem controle sobre pipelines de retreino automático e decisões de deploy.
